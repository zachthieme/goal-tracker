# Changelog

**Reading this file.** Every change that ships is logged, internal work included,
and each entry opens with a tag saying who it reaches:

| Tag | Visible to |
| --- | --- |
| `[user]` | someone **using** Goal Tracker: web UI, emails, observable behaviour |
| `[ops]` | someone **running** it: env vars, migrations, deploy steps |
| `[api]` | a **programmatic contract**: the spreadsheet import format, database schema, configuration |
| `[internal]` | nothing externally observable: refactors, CI, tests, docs, plumbing |

`**Breaking changes:**` comes first in a milestone and names the contract it broke.
The format is in [`docs/changelog-conventions.md`](docs/changelog-conventions.md).

### Collected changes — October 2, 2026

**Breaking changes:**
- [api] **Spreadsheet import format**: a column naming a Retired Dimension is now rejected for the whole file, like any unknown column, where before it was matched and only its non-blank cells failed. In a Dimension's column a semicolon now separates values, so a value whose name contains a semicolon can't be imported. Drop a Retired Dimension's column from the spreadsheet before importing (#77).
- [api] Spreadsheet import format: a column headed `ID` is now always read as the Goal id column, so a Dimension or Field named "ID" can no longer be set from a spreadsheet; rename it to import it (#81).
- [api] **Spreadsheet import format**: a Dimension value can no longer contain a semicolon, since the import separates values with one; there is no escape for it. Before, such a value could be created in the app, but a download writing it could not be imported again. A download of Goals carrying one is now refused, naming the Dimension and the value; rename the value on the Dimensions page to a name without a semicolon, then download again (#101).

**New features:**
- [user] An Admin now chooses, per Dimension, whether a Goal takes one value or several: the define-a-Dimension form offers "one value" (the default) or "several values", and each Dimension card's Edit toggle switches it. Switching back to one value is refused while any Goal carries more than one value in that Dimension, and the refusal links each of those Goals. Existing Dimensions take one value (#69).
- [user] On the Goal page a several-values Dimension shows a checkbox per value, saved together, so an Owner can give a Goal several values and remove one; a one-value Dimension keeps its select and still replaces the Goal's previous value. Grouped by a several-values Dimension, the Goal list shows a Goal under each of its values, and the list's new total counts each Goal once. Filters and Report Definitions still OR values within a Dimension, so a Goal carrying a value among several is still selected (#69).
- [api] Database schema: migration `0021_dimension_selection` adds a `selection` column to `dimensions` (`'one'` or `'several'`, default `'one'`). It's additive and runs on startup; every existing Dimension keeps taking one value (#69).
- [user] An Admin now makes each Dimension's list Fixed (only Admins add values, the default and every existing Dimension) or Extendable, on the define-a-Dimension form or from each card's Edit toggle, and can switch either way at any time; switching back to Fixed only stops further additions. On the Goal page an Extendable Dimension, one-value or several-values, has an "add a value" input beside its choices that adds the value and sets it on the Goal in one step (#70).
- [user] A Goal's Delegates can now set its Dimension values, and add to an Extendable list, as its Owner and Admins can; Contributors still can't. Renaming and retiring values stays with Admins (#70).
- [api] Database schema: migration `0022_extendable_dimensions` adds a `list` column to `dimensions` (`'fixed'` or `'extendable'`, default `'fixed'`). It's additive and runs on startup; every existing Dimension stays Fixed (#70).
- [user] An Admin now sets the order of a Dimension's values from each card's Edit toggle on the Dimensions page, with move-up and move-down buttons per value and a "Sort alphabetically" action. Values are listed in that order everywhere: the Goal page, the Goal list's filter, and its groups. Existing values start in today's alphabetical order (#71).
- [user] An Admin can merge one Dimension value into another in the same Dimension from the Edit toggle, after confirming: every Goal carrying the merged value carries the target instead (once, if it had both), every Report Definition filter on it points at the target, and the merged value is removed. It's all or nothing, and merging across Dimensions is refused (#71).
- [api] Database schema: migration `0023_dimension_value_order` adds a `position` column to `dimension_values`, the value's place in its Dimension's list, starting every existing value in alphabetical order. It's additive and runs on startup. A merge is the one action that deletes a `dimension_values` row, after moving its `goal_dimension_values` and `report_definition_filters` rows to the target (#71).
- [user] An Admin can now retire a whole Dimension from its card's Edit toggle on the Dimensions page, after confirming. A Retired Dimension isn't offered for setting a Goal's values, as a child Goal's default, in the Goal list's filter and grouping, or in the Report Definition form, and the Dimensions page flags it retired. Goals carrying its values still show them, marked retired on the Goal page and in the Goal list. Saved Report Definitions that filter on its values keep selecting the same Goals. Nothing is deleted (#72).
- [user] An Admin can reverse any retirement: a Retired Dimension and a Retired value each get a Restore button behind the Edit toggle, and restoring returns them everywhere they were withdrawn from (#72).
- [api] Database schema: migration `0024_retired_dimensions` adds a `retired` column to `dimensions` (0 or 1, default 0), so every existing Dimension stays in use. It's additive and runs on startup (#72).
- [user] Admins can now define Fields: values typed directly on a Goal to describe it, such as a budget or notes. A new Fields page, linked from the Admin page, defines a Field with a name and one of four types: number, short text, long text or date. A number Field can have an optional unit (e.g. "$", "FTE"). The type can't change later, and a Field can't take a Dimension's or another Field's name, whatever the letter case. Non-Admins can see the Fields page but can't define Fields (#73).
- [user] The Goal page has a Fields block in the sidebar that lists every Field. A number shows with its unit, a short text that is an http(s) URL is a link, and a long text keeps its line breaks. The Owner, Delegates and Admins set or clear each value under "Edit Fields", which can also be opened from the More menu. Each Field gets an input for its type. Everyone else sees the values read-only. A number that doesn't parse as a number, or a date that isn't a date, is refused with a message naming the Field. Fields aren't on the Check-in form or in the Goal list's filter and grouping, because they describe a Goal rather than slice it or update it (#73).
- [user] An Admin can retire a Field from its card on the Fields page after confirming, and restore it later. A Retired Field isn't offered for entry, but Goals that already have a value in it still show that value, marked retired. Nothing is deleted (#73).
- [api] Database schema: migration `0025_fields` adds a `fields` table (`name`, `type` of `'number'`, `'short_text'`, `'long_text'` or `'date'`, `unit`, `retired`) and a `goal_field_values` table holding one text value per Goal and Field. It's additive and runs on startup (#73).
- [api] **Spreadsheet import format**: the import follows the Goal page's rules for Dimensions and Fields. A column whose header names a Field sets that Field; a number or date that doesn't parse is reported on its row. In a Dimension that takes several values a cell lists them separated by semicolons (`Growth; Trust`); more than one in a one-value Dimension is a row error. A value not in an Extendable Dimension's list is added to it by the importing Admin, last in the order; in a Fixed one it's still a row error. Values match whatever their letter case or surrounding spaces, and an import that saves nothing adds no values. A Retired Field's column is rejected like any unknown column. `docs/import-format.md` describes the new columns (#77).
- [user] The Import page says how Dimension and Field columns are read, including the semicolon separator and the Extendable rule (#77).
- [user] The Goal list has a Table layout: one row per Goal with its Title, Owner, Health, Lifecycle, delivery date and last Check-in, then a column for every live Dimension and Field. A List / Table toggle switches layout and keeps every filter, and the layout, filters and sort are all in the URL, so a table link can be shared. Click a column header to sort by it and click it again to reverse; numbers and dates sort as numbers and dates, and Goals with no value sort last. The Columns control hides any column except Title, and your browser remembers the choice without needing JavaScript. The table is read-only, isn't grouped, and has no totals row (ADR 0005) (#79).
- [user] A Goal's page has a collapsed "Value history (N)" section, beside "Ownership history", listing every change to its Dimension values and Fields oldest first: who made it, shown by Name, when, and the value before and after. A Delegate's change is credited to the Delegate, a value added or removed in a several-values Dimension reads as "added X" or "removed X", and saving without changing anything adds nothing. Entries keep the values as they were, so renaming or merging a value later doesn't rewrite them. Values set by a spreadsheet import are credited to the importing Admin. Changes made before this release have no history (#74).
- [api] Database schema: migration `0026_goal_value_changes` adds a `goal_value_changes` table, one row per change to a Goal's Dimension values or Fields: `actor_id`, `dimension_id` or `field_id`, the Dimension's or Field's name and the values before and after as text at the time, `several` for an add or remove in a several-values Dimension, and `created_at`. It's additive and runs on startup, and isn't backfilled (#74).
- [user] A Theme menu in the top bar, beside Sign out and on the sign-in page too, pins the site to Light or Dark or leaves it following your system. The choice is kept in this browser for a year, holds across signing out, and shows from the first paint; a Report's Print view stays black on white (#84).
- [user] The Goal table has a "Download CSV" link that downloads the Goals its filters keep, one row each, in the spreadsheet import format with a leading ID column and a column for every live Dimension and Field, hidden columns included. Several values are separated by semicolons and Owners are written as emails. Editing a Dimension or Field cell and importing the file again updates that Goal, recording each change in its Value history; the import page counts the Goals updated and says once which other columns it ignored (#81).
- [api] Spreadsheet import format: an optional `ID` column. A row with an ID updates that Goal's Dimension values and Fields from the row, following the Goal page's rules, an empty cell clearing the value; its other columns are ignored and named once in the result. A row without one creates a Goal as before, and an ID matching no Goal is a row error that fails the file. See `docs/import-format.md` (#81).
- [user] The Goal table has an "Edit values" control that turns it into one form for changing Dimension values and Fields without opening each Goal. Rows for Goals you own, are a Delegate on, or (as an Admin) any Goal get an input in each Dimension and Field cell, Extendable Dimensions included; other rows stay read-only, and Title, Owner, Health, Lifecycle and delivery date are never editable there and link to the Goal. One Save applies every changed cell by the Goal page's rules and records each change in the Goal's Value history. It is all or nothing: if any cell is invalid, nothing is saved and the form comes back as typed with each bad cell marked. It works without JavaScript (#80).
- [user] An Admin can mark a Dimension or a Field required, and unmark it, from its card on the Dimensions or Fields page. A Proposed Goal can't be activated while it lacks a value in a required Dimension or Field that isn't Retired: the activation checklist lists each one, and the refusal names what's missing. Marking something required never blocks anything already Active; an Active Goal without a value is flagged Incomplete instead, with a quiet badge on its row in the Goal list and a note on its page naming what it lacks. The flag doesn't change the list's sort order, clears as soon as the value is set or the Dimension or Field is unmarked, and never appears on Proposed, On Hold, Done or Cancelled Goals. The Goal list has an "Incomplete" filter showing exactly the Incomplete Goals. Spreadsheet imports and value changes are never refused for a missing required value (#75).
- [api] Database schema: migration `0027_required_values` adds a `required` column to `dimensions` and to `fields` (`0` or `1`, default `0`). It's additive and runs on startup; nothing is required until an Admin marks it (#75).
- [user] A Definition log, linked from the Admin page and readable by anyone signed in at `/definition-log`, lists every change to what Dimensions and Fields exist and how they're shaped, newest first, each with who made it, when, and a sentence saying what changed: a Dimension or Field created, retired or restored; a Dimension switched between one value and several or between Fixed and Extendable; a Dimension or Field marked required or not; and a value added, renamed (old and new name), retired, restored, merged (both values) or moved, with "Sort alphabetically" as one entry. A value an Owner or Delegate adds to an Extendable list from a Goal is logged with them. A form narrows the log to one Dimension or Field. Nobody can edit it, refused changes and changes that change nothing aren't logged, and values set on Goals stay in each Goal's Value history. Defining a Dimension with several values or an Extendable list is one entry. Changes made before this release aren't in the log (#76).
- [api] Database schema: migration `0028_definition_log` adds a `definition_changes` table (actor, the Dimension or Field it's about, a summary sentence, time), with triggers refusing any `UPDATE` or `DELETE` on it. It's additive, runs on startup, and starts empty (#76).
- [user] A Report Definition can show chosen Fields beside each Goal. The New Report Definition form lists the Fields still offered (none Retired), and the ones ticked appear as labelled values on each Goal that has a value in them, in both the exception card and the one-line On track row: a number with its unit, a long text with its line breaks, never in the narrative. A Field a Goal has no value in is left out, not shown blank, and number Fields are never totalled. A publication freezes the Field names, units and values it showed, so editing a value, renaming the Field or retiring it later doesn't change it; the publication page, the Print view and the Markdown export all carry them. A Report Definition with no Fields chosen reads as before, and one whose chosen Field is retired later keeps showing it (#78).
- [api] Database schema: migration `0029_report_definition_fields` adds a `report_definition_fields` table (Report Definition, Field) holding the Fields each Report Definition shows. It's additive, runs on startup, and starts empty, so existing Report Definitions show no Fields. Published snapshots gain an optional `Fields` list on each Goal; earlier snapshots read as before (#78).
- [user] Removing a link between Goals and retiring a Dimension value now each offer Undo: the page shown straight after carries a toast at the bottom of the window saying what was done, with an Undo button that works without JavaScript. The toast shows only that once; a reload or a later visit drops it. Undo on a removed link puts it back as accepted without asking the parent's Owner again, and only the person who removed it may, once, while they still own one of its Goals; it is refused with a message if the link exists again or would now create a cycle. Undo on a retired value restores it (#83).
- [api] Database schema: migration `0030_link_removals` adds a `link_removals` table recording each removed link (its two Goals, note, requester, who removed it and when, and when it was undone). It's additive and runs on startup; links removed before it leave no record and can't be undone (#83).
- [internal] The toast is one shared component, `toastNotice` in `layout.templ`, offered through the one-time `gt_undo` cookie and described in `DESIGN.md` § Components, for the Undo on rejects to reuse (#83).
- [user] A Check-in can carry any number of Highlights, in any mix of Insight, Accomplishment and Miss, kinds repeating. The form's Highlight section starts with one row, and "Add another" adds a row while keeping everything already typed and recording nothing; it works as a plain form post without JavaScript. A row left with a blank note is ignored, and a note with no kind is refused, naming its row. The Goal page lists each Highlight on its own, in the order entered, and a Report author picks each into the narrative separately, so one can be pulled from a Check-in and another left out. Highlights recorded before keep their Check-in, kind and note, and frozen publications are unchanged (#104).
- [api] Database schema: migration `0031_several_highlights` rebuilds `highlights` without the `UNIQUE` on `checkin_id`, so a Check-in may have several rows; each existing row is copied with its `id`, so `narrative_picks` still find it. It runs on startup. Within a Check-in, Highlights read in `id` order, the order entered (#104).
- [user] Rejecting a link request or a Handoff now offers Undo: the page shown straight after (Home, or the request's pending page, whichever you rejected from) carries the same toast as removing a link, saying what was rejected, with an Undo button that works without JavaScript and shows only that once. A Reject from Home now returns to Home rather than the pending page. Undo puts a link request back as pending with its original note and requester, and a Handoff back as pending to the same proposed Owner, shown as pending in the Goal's ownership history. Only the person who rejected it may undo it, once; it is refused with a message if the link has been requested or accepted again since or would now create a cycle, or if the Goal has another pending Handoff, has changed Owner, or its proposed Owner has Departed. Rejecting tells no one, so neither does the Undo (#96).
- [api] Database schema: migration `0032_rejected_link_requests` adds a `rejected_link_requests` table recording each rejected link request (its two Goals, note, requester, when it was made, who rejected it and when, and when it was undone). It's additive and runs on startup; requests rejected before it leave no record and can't be undone (#96).

### Collected changes — October 1, 2026

**New features:**
- [ops] `make restart` rebuilds the server and restarts the tailnet instance in the background. It stops whatever listens on `127.0.0.1:$SERVE_PORT` and runs `make serve` detached, logging to `serve.log`. It waits until the new server is listening and fails, showing the log, if it doesn't come up.
- [user] The Goal page has a collapsed "Ownership history (N)" section listing every Handoff and Admin Reassign oldest first, with from, to, who started it, when, and the outcome: pending, accepted, rejected, cancelled, or reassigned by an Admin (#46).
- [user] An Admin can reverse a departure: a Goal page whose Owner has departed offers "Mark returned…", which asks for confirmation. The person can sign in again and the Goals they still own stop being Ownerless; a Goal reassigned while they were away stays with its new Owner, and a cancelled Handoff stays cancelled (#45).
- [user] Pages show people by their Name instead of their email address, with the email on hover; someone without a Name yet is shown by the part of their email before the `@`. The Markdown export, the Print view, and the reminder, digest, and comment emails introduce each person as `Name (email)` at their first mention. Publications keep the Names people had when published, and ones published earlier still show emails. Forms and the spreadsheet import still take emails, and the seed gives every person a Name (#41).
- [user] Accepting a Handoff now lets the new Owner choose which of the Goal's Delegates to keep. The accept form, on the pending Handoffs page and on Home, lists each Delegate who hasn't left the org with a keep box checked by default. Unchecked Delegates are removed in the same step as the ownership change, and if accepting fails nothing changes. A new Owner who was a Delegate on the Goal stops being one. Departed Delegates aren't offered and stay on the Goal. Rejecting a Handoff and an Admin Reassign leave every Delegate in place (#47).
- [user] The Admin page lists every Departed person, with a "Mark returned…" button for each, so an Admin can return someone who owns no Goal — a Delegate, or an Owner whose Goals were all reassigned while they were away — without a Goal page to do it from (#51).
