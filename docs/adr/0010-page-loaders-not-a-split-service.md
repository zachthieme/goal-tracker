# Keep one Service, and give a page that repeats reads a page loader

In October 2026 a code review (#429) flagged that `domain.Service` had 336 methods with no internal boundaries, and proposed a read model per page in front of it. By the time #411 had batched the list pages it had 389 methods (238 exported) across 53 files in `internal/domain`. Batching made the list pages flat: Home makes 41 queries, the Goal list 39 and Follow-ups 44, the same for 10 Goals as for 50, and the `querycount_*_test.go` tests pin those counts. The Goal page did not get flatter. Its view model (`goalPageView` in `internal/web/goalpage.go`) calls about 47 `Service` methods, each loading what it needs, so one view runs 82–88 queries, only about 50 of them distinct:

- `GetGoal` 7 times, `GetAccount` 4 times, `ListMilestoneChangesByGoal` 4 times, and `ListCheckins`, `ListChildGoals`, `ListAccountsUnder` and `ListDelegatedGoals` 3 times each;
- the whole-org reads `ListGoals` and `ListActiveGoalsWithLatestCheckin` twice each.

(Measured on `main` at 71a65bf with a probe through `newQueryCountingServer` and `seedQueryCountFixture(t, h, 10)`.)

We decided to keep `Service` one type, with one file per concept, and not to add a general read-model layer. The method count alone is not a problem worth fixing. The per-concept files are what keep campaign waves free of conflicts (CLAUDE.md, Code layout), and splitting the type would touch almost every file in `internal/domain` and `internal/web`. List pages are already flat through batching, and ADR 0009 keeps queries in-process and cheap, so a repeated query is a cost in tidiness before it is a performance problem. Instead, a page that repeats reads, as the Goal page does, gets its own page loader.

## Consequences

- **What a page loader is:** one `Service` method that returns everything the page shows. It lives in its own `internal/domain/<page>.go` file and reads each thing once. It reuses the existing pure helpers, and checks the viewer's permission once, as the separate methods do today. The web handler builds the view from that one result, and a `querycount` test pins the loader's query count.
- **A page earns a loader;** it isn't given one in advance. A page gets one only when a probe shows it repeating reads. Mutators, and pages that don't repeat reads, stay on the ordinary `Service` methods.
- **The Goal page is the first** (#462).
- **The Check-in page is the second** (#560). Its form had been assembled on four paths: the page, the error re-render, "Add another" and the refused No change. They ran the whole Goal page loader or a handful of separate `Service` calls, 49–63 queries each. Now each path calls `Service.CheckinPage` once, for 24 queries, or 28–31 when the command it posted refused. Checking it against the second-loader trigger below: the two loaders share the people lookup (`goalPageAccounts`) and the pure helpers that judge the Rolled-up Health, Run off Green and No change (`rollUp`, `runOffGreen`, `noChangeFactsOf`, `judgeNoChange`). They share no type and no reading layer, because each reads only what its own page shows: 11 queries for the Check-in page against the Goal page's 36. Sharing more would make the Check-in page read the Goal page's history.
- **The Report draft page is the third** (#606). Three paths rendered it, the page, a refused Report Delegate add and a plain Add another, and each read it through a handful of separate `Service` calls. A probe (on 477eb3a, with `seedQueryCountFixture(t, h, 10)` and its Admin, less the session's 2 queries and the sidebar's 11) counted 39 queries, 27 distinct: `ListCheckinsForGoals` 4 times, `GetAccount` and `ListMilestonesForGoals` 3 times each, and `GetReportPublication`, `LatestReportPublication`, `ListDateSlipsForGoals`, `ListLatestCheckinsForGoals` and `ListOpenActionItems` twice each. Some of those are `DraftReport`'s own. The rest are the page's parts reading again what another had read: the discussion read the open Action Items the draft had, the Goals panel's `SummarizeReport` read the publication and the Goals' Check-ins, Milestones and Date Slips again for counts the page doesn't show, and the permissions read the viewer twice. With an open Action Item, judging it read the Report Definition and its Report Delegates again too. Now each path calls `Service.ReportDraftPage` once, for 28 queries, or 33 with the Report Definition the path names. The repeats left are `DraftReport`'s own, which stay because it drafts for publishing and the Report list too, and `GetAccount` twice: the draft's Ask for help addressee and the viewer, each looked up by itself. Checking it against the second-loader trigger below: it shares the rules with `ReportPermissions` and `ActionItemPermissions` (`editReportRefusal`, `reportDelegatesRefusal`, `permitActionItems`) and `goalPagePermits` with the Goal pages' loaders, and no type or reading layer with them: they read a Goal, it reads a Report Definition.
- **The Goal definition page is the fourth** (#629). Four paths render the New goal form: the New goal page with the parents `?parent=` picks, a refused create, the define page that finishes a Proposed Goal, and a refused define. First the New goal page read its picked parents' values in one query (`ListGoalValuesForGoals`, in `Service.SuggestedValues`), not one each, and the define page's live checklist stopped reading the parents and candidates its card doesn't show. A probe then (on bfb5f8f, with `seedQueryCountFixture(t, h, 10)`, the New goal paths for its Admin and the define paths for Priya, who owns its Proposed Goal 00, less the session's 2 queries and the sidebar's 11) counted: the New goal page with 3 picked parents 6 queries, 6 distinct, as many as with 1 (8 before, `ListGoalValues` 3 times); a refused create posting 3 parents 8, 6 distinct, `GetGoal` 3 times, `CreateDefinedGoal`'s own check of each parent; the define page 14, 12 distinct, `ListParentGoals` and `ListPendingParentLinks` twice each, because the page read its parent links and `ParentCandidates` read them again; and a refused define posting a parent 19, 14 distinct, `GetGoal` and `ListParentGoals` 3 times and `ListPendingParentLinks` twice. (`ParentCandidates`' cycle check no longer runs `ListParentGoals` per candidate, since #638.) The live checklist, which reads no sidebar, went from 12 queries to 6 past the session's: the Goal, its Milestones and Metrics, and the Dimensions, their values and the Fields. The define page repeated reads, so now its two paths call `Service.GoalDefinitionPage` once: the define page runs 12 queries, 12 distinct, none twice, and a refused define 19, 15 distinct, whose repeats are all `DefineGoal`'s own reads in its refused transaction (`GetGoal`, `ListGoalValues`, `ListGoalFieldValues`, `ListParentGoals`). The New goal paths repeat nothing of their own and stay on the ordinary methods. Checking it against the second-loader trigger below: it reads some of what the Goal page's loader does, the Goal's values, Fields, Milestones, Metrics and accepted parents, through the same `Service` methods, and shares `ParentCandidates`' rule (`parentCandidatesOf`), but no type or reading layer: it reads none of the Goal's history, Check-ins or discussion, 11 queries against the Goal page's 36, and the Goal page doesn't read Pending parents or candidates.
- **What triggers a revisit:** any one of
  - a page whose query count grows with the number of Goals, which batching should handle first;
  - a second page needing a loader with the same shape as the first, at which point consider whether loaders should share anything.

  "`Service` has too many methods" is not a trigger.
